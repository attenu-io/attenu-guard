# 0.23.0 — 2026-11-25

The source of Internet-Draft -04, the fully-specified Ed25519 identifier under profile "02", three step-5 boundary vectors and a `steps` member in every -02 vector. The entries below are the CHANGELOG text for this release.

### Changed
- **Profile "02": an Ed25519 key signs as `"Ed25519"`, not `"EdDSA"`** (RFC 9864; the -03's Section 3 and step 1 require a fully-specified algorithm). `serialize`/`serialize_chain(..., draft="02")` write `"Ed25519"` in the header; `wire.load(..., draft="02")` defaults its accepted list to `["Ed25519"]`, so a -02 chain minted by 0.22.0 or earlier (header `"EdDSA"`) is now `signature_invalid` by default. To keep accepting those until they expire, pass `accepted_algs=["Ed25519", "EdDSA"]`: the alg-confusion guard admits both names of the signer's own algorithm, never another key type. The default -01 profile is unchanged (`"EdDSA"`), and so is the evidence envelope's `witness.alg`. Found by the visado interop harness (case A.9). Tests: `tests/test_wire_02.py` `FullySpecifiedEd25519`

### Added
- **`docs/draft-asor-wimse-agent-delegation-chain-04.md`**: the -04 source. Section 4.2 states that a token descended from one carrying `max_lifetime` starts its own total, so a delegable token does not bound the tree with it (Kieran Sweeney, 2026-11-20); step 8 requires the component holding shared accounting to check and debit every earlier token's `max_subtree`, admits an allocation from a single-writer allocator in place of a held total, and denies outside both shapes of Section 9.4; Section 11 records visado as a third implementation and the Ed25519 identifier change; Appendix B the three vectors and the `steps` member; Changes Since -03
- **Three step-5 boundary vectors** in the -02 set (now thirty-nine files): `valid_now_before_exp` (`now` 299, accept), `reject_now_equals_exp` (`now` 300, `expired`) and `reject_now_after_exp` (`now` 301, `expired`), each `valid_chain.json`'s tokens unchanged with `now` moved. No earlier vector reached the upper bound of step 5. `VECTOR_NAMES_02` lists them
- **A `steps` member in every -02 vector file**: the checks of Section 6 a verifier performs to reach the file's outcome (`exercised`, in order, up to the deciding check) and the rest (`not_exercised`, always including steps 6, 7 and the authority half of 8), so a result file can state the boundary its verdict supports. Informational; scorers ignore it. The `tokens` of the thirty-six earlier files are byte-identical. Format in `tests/vectors-02/README.md`

## Migration

A -02 chain minted by 0.22.0 or earlier with an Ed25519 key says `"alg": "EdDSA"` and is now `signature_invalid` under `wire.load(..., draft="02")` by default. Pass `accepted_algs=["Ed25519", "EdDSA"]` while such tokens are still unexpired. The -01 profile is unchanged.
