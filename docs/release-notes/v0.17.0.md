# 0.17.0 — 2026-09-20

One change: a verifier no longer reports success on a token it did not fully read.

## What was wrong

`load()` reconstructed the Authority from `authorization_details[0]` and never
looked at the rest of the array. A token carrying `agent_delegation` first and a
second authorization detail after it was accepted, and the second entry was
discarded without an error, a warning or a ledger line.

That is fail-open in exactly one direction, and it is the dangerous one. An
ignored entry that **restricts** authority is lost, so the chain permits more
than the issuer allowed. An ignored entry that **grants** extra authority is
harmless, because ignoring it leaves the chain more restrictive. Only the
harmful direction was silent.

## How it was demonstrated

Not inferred from reading the code. On the released `valid_chain` vector that
ships in this package, with a control run first to prove the re-signing method
itself was sound:

```
CONTROL  leaf re-signed, unchanged  -> ACCEPTED
MUTATED  one foreign detail appended -> ACCEPTED   <- silently discarded

  details actually in the signed token : ['agent_delegation', 'wes_enterprise_policy']
  leaf authority the verifier read     : ['crm.read']
  permits('crm.read')                  : Decision(allowed=True, reasons=())
```

The appended detail said `deny_scopes: ["crm.read"]`. The verifier reported
success and permitted the action the issuer's own detail forbade.

**RFC 8785 canonicalization is not what stops this.** A first attempt at the
reproduction was rejected `non_canonical`, but only because it re-serialized the
payload with `json.dumps`. Going through `canonical.dumps` produced a token the
verifier accepted. An issuer adding a detail through a conforming JCS path sailed
straight through, so the guarantee had to come from a rule about detail types,
not from canonicalization. Both test suites now assert the refusal reason is
never `non_canonical`, so a future change cannot let canonicalization quietly
stand in for the real rule.

## Why it mattered more than a tidiness bug

The Internet-Draft points implementers at exactly this route. The last paragraph
of "Scope Syntax and Wildcards" says:

> This wildcard-covering rule applies only to the "scopes" member of the
> "agent_delegation" authorization detail type defined in {{authority}}; other
> authorization detail types, if defined, specify their own scope semantics.

So a deployment carrying its own policy vocabulary as a second detail type was
being told to take a path that failed open in the reference implementation. It
was found while answering an IETF list reviewer who asked whether scope
evaluation could stay pluggable, and the honest answer turned out to be that the
sanctioned alternative did not work.

## It was worse than the array

The first fix refused a token carrying more than one authorization detail. A
code review of that fix found it stopped at the array boundary, and the
identical fail-open was still live one level down, inside a **single**
`agent_delegation` entry — because the loader cherry-picked `scopes` and
`constraints` and discarded every other member.

That is not shape-hunting. RFC 9396 section 2 gives every authorization detail
object a set of common members — `actions`, `locations`, `datatypes`,
`identifier`, `privileges` — and this draft's token format says "An array of
authorization detail objects {{RFC9396}}". An issuer expressing a restriction
the RFC-sanctioned way was having it silently dropped. Verified against the
released vector before the second fix: a leaf carrying `deny_scopes`, or
`actions` plus `locations`, or `critical: true`, verified clean and still
permitted the scope the extra member existed to restrict. `critical` is the
worst of them — the member whose whole meaning is "do not ignore me".

One level deeper again, a constraint object carrying two typed values kept one
and dropped the other:

```
{"key": "max_rows", "max": 100, "min": 9999}  ->  {"key": "max_rows", "max": 100}
```

byte-identical to a constraint that never carried a floor, so nothing
downstream could tell. `min` is a first-class type in the draft's constraint
vocabulary ("the value MUST NOT be less than it"), and the draft allows one
typed value per object — so two is malformed and must be refused, not silently
resolved to whichever one this build happens to read first.

## The rule now

Three levels, one principle: **refuse what we would only partly read.**

1. More than one authorization detail → `malformed`. Two `agent_delegation`
   entries are refused for a second reason: the draft says Authority is
   expressed by *an* authorization detail of that type and never says which
   element to take when several are present, so taking the first silently
   nominated a winner the document does not.
2. A member inside the `agent_delegation` detail beyond `type`, `scopes` and
   `constraints` → `malformed`.
3. A constraint object carrying a **member** this build does not read → parse
   it, re-emit it, and refuse if the input had a member the re-emission does not
   → `malformed`.

Every message names what could not be evaluated: a denial a deployer cannot act
on is only half a fix.

Rule 3 tests a **member difference, not value equality.** The first attempt
compared whole values, and a second review round caught it rejecting
*conformant* tokens: it could not tell "we ignored a member" from "we normalised
a value", and three built-ins legitimately normalise — `Allow` and `Deny` emit
`one_of` / `not_one_of` sorted and hold them as sets, and `to_wire` omits `field`
when it equals `key`. RFC 8785 canonicalises object member *order* and never
reorders array elements, and the draft puts no ordering or uniqueness
requirement on `one_of`, so `["us-west", "us-east"]` is a perfectly conformant
constraint from a third-party issuer and the first rule called it `malformed`.
On a release whose whole subject is reading tokens correctly, refusing correct
tokens is the worse failure. `field` carries one further exemption: it is read
and then not re-emitted when it equals `key`, so it counts as dropped only when
the ceiling did not actually resolve to it.

An unrecognised constraint **type** is deliberately not caught by rule 3.
`_UnknownCeiling` preserves its whole object, so it round-trips and still routes
to the fail-closed path the draft requires — "a verifier that encounters an
unknown constraint type MUST treat the action as denied (fail-closed), never as
unconstrained." Turning those into a parse error would lose the deny.

This is the same shape and the same place as the draft's existing requirement
for an invalid scope — "A verifier that encounters one MUST reject the
Delegation Token as malformed before evaluating subsumption."

**Refusing is the loosenable direction.** If a future revision defines
ignorable/critical marking, in the spirit of RFC 9396, then accepting more is a
backward-compatible change. Starting permissive and tightening later would not
have been. The fix deliberately does not pre-empt that decision.

## Migration

This is a wire-behaviour change: a token that verified before is refused now.

Nothing published is affected. No vector under `src/attenu_guard/vectors/` or
`tests/vectors/` carries more than one authorization detail — every token in
every vector was decoded and checked — and the library has never emitted more
than one.

If you mint tokens with something other than this library and you put more than
one authorization detail in them, they will now be rejected as `malformed`. The
entries named in the error are the ones this verifier could not evaluate.

## One API change, and the caller sweep it needed

`Authority.from_wire` is now **partial**: it raises on a constraint carrying
members this build does not read. That is the fix, and on the token path
`load()` wraps it into `WireError(MALFORMED)` exactly as before.

It matters beyond the token path because `Authority.from_wire` is public API and
a bundle is untrusted input. Making a widely-used constructor partial is an API
change, and the first version of this release did not sweep its callers. Every
call site in both repos has now been checked:

| call site | state |
|---|---|
| `wire._authority_from_payload` (Python), `authorityFromPayload` (TS) | already guarded → `WireError` |
| `evidence` authority/granted reconstruction (both ports) | already guarded → reported as a verify failure |
| `adapters/a2a.py` ×3 | **was unguarded — fixed** |

The `a2a` sites raised a `ValueError` straight out of functions documented to
return `(bool, failures)`, so a caller correctly handling a failure list got an
exception. They report now, and "unreadable" is distinguished from "absent":
both fail closed, but `holds None` for a constraint we could not parse misnames
the reason.

Nothing exercised those paths, which is why a code review found them by reading
rather than a test by running: the `a2a` extra is not installed in the default
dev environment, so the whole adapter is skipped and a green suite said nothing
about it. It has its own tests now, confirmed red before the fix.

**If you call `Authority.from_wire` directly on untrusted input, guard it.**

## Migration, in one line

If you mint tokens with something other than this library, a token is now
refused as `malformed` when it carries more than one authorization detail, any
member in the `agent_delegation` detail beyond `type` / `scopes` / `constraints`,
or a constraint object carrying anything this build does not read. The error
names the offending members.

## Verification

- **578 tests pass**, including the Hypothesis invariants.
- New `tests/test_unknown_detail_types.py` (19 tests). The assertions covering
  the new behaviour were confirmed RED before each fix, with the controls
  passing — the file deliberately contains controls that passed all along (the
  unmodified vector, a foreign type in first position, which was already
  rejected), so "every test was red" would be false.
- Each suite carries three guards against a hollow pass: a **control** that
  re-signs the leaf unchanged and still verifies, so a rejection cannot merely
  mean the test signs badly; an assertion that the refusal reason is **never
  `non_canonical`**, so canonicalization cannot quietly stand in for the real
  rule; and the **released vector driven through `load()`** rather than a unit
  call on an internal helper.
- The identical rules landed in `attenu-guard-ts` 0.11.0 in the same change.
  Both ports were checked directly to accept and refuse the **same eight cases**
  byte-for-byte through `load()`, on the same chain and the same bytes:
  unmodified, a second detail entry, a second `agent_delegation` entry,
  `deny_scopes` inside the detail, `actions` inside the detail, `critical`
  inside the detail, a second typed value inside a constraint, and an unknown
  member inside a constraint.
- Regression surface checked by decoding every token of every vector under
  `src/attenu_guard/vectors/` and `tests/vectors/`: maximum detail array length
  is 1, no detail carries a member outside `{type, scopes, constraints}`, and
  all 116 constraint objects survive the member check.
- **That 116 was a vacuous pass and is recorded here so it is not trusted
  again.** No vector or fixture in either repo carries an `allow`, `deny` or
  `prefix` constraint, so it only ever exercised the four ceilings that emit
  exactly what they read. The three ceilings that normalise were never touched
  by it, which is precisely why the first version of rule 3 looked clean while
  rejecting conformant tokens. Those cases now have explicit tests in both
  ports rather than relying on vector coverage that does not exist.

## How this was found

While answering an IETF list reviewer who asked whether scope evaluation could
stay pluggable. The honest answer was that the draft's sanctioned alternative —
register your own authorization detail type — did not work in the reference
implementation. The first fix was shipped to `main` and then found incomplete by
an adversarial review of its own diff, before it was tagged. Both halves are in
this release.
