# 0.20.0 — 2026-10-15

The -02 revision of the Internet-Draft (draft-asor-wimse-agent-delegation-chain-02), as an
opt-in profile beside the -01, and its own vector set. The -01 stays the default on every
path. Three cross-language fixes ride along (attenu-ops #127).

## The -02 profile, opt-in

Pass `draft="02"` to `wire.load`, `wire.serialize` and `wire.serialize_chain`, or
`profile="02"` to `Authority`. Nothing else changes: without it, every call takes the -01 path
it took in 0.19.2, the twenty published -01 vectors verify byte for byte as before, and the
hardening of 0.19.0 and 0.19.1 (one constraint per key, typed members, closed details) is not
relaxed there. A chain minted under one profile is `malformed` under the other. There is no
transition mode, as the draft says, and an `Authority` of one profile never meets one of the
other (`meet` raises, and `Guard.delegate` records `spawn_denied` and raises).

What the -02 adds, as this library implements it:

- **Who acts, for whom.** The Principal is in `sub` and must be identical at every hop
  (`principal_altered` on any change); the Acting Agent is in `client_id`.
- **Audience.** `aud` is a string or a non-empty array (null is `malformed`). The leaf's
  audience is checked against `load(audience=...)` and `VerifiedChain.permits(audience=...)`
  (`audience_mismatch`); under `"02"`, `permits` denies unless an audience was supplied at one
  of the two.
- **Holder binding claim.** `cnf` on every token, carrying `jkt`, `jwk` or `x5t#S256`. Its
  presence and shape are checked; steps 6 (holder binding) and 7 (status list) are not
  performed, as before.
- **Accepted algorithms.** Step 1 takes a list (`accepted_algs`, a list or tuple of strings,
  defaulting to the signer's own algorithm) and denies an off-list `alg` even where the
  signature verifies. Under `"01"` the list is honoured only when given.
- **Three scope forms.** Literal, wildcard and opaque. An opaque scope is an RFC 6749
  scope-token without `*`, covered only by a byte-identical child scope and never by a
  wildcard. No case folding, and no trailing newline (`crm.read\n` is no scope).
- **Constraint types.** `max_lifetime` and `max_subtree` beside the per-action `max`, with no
  inference across types. `CallLimit` is emitted as `max_lifetime`, since its -01 wire form,
  `max`, is the defect the -02 names. `rank` carries its `order` on the wire, and a child's
  order is identical to its parent's. One constraint per (key, type): a `min` and a `max` on
  one key form a range, while two of one type stay `malformed`.
- **Closed objects.** Closed constraint objects, and exactly one detail, of type
  `agent_delegation`; any other type is `malformed` at parse, before step 1, so DT_0 is
  covered.
- **Outcome names.** Each denial is named as the -02's Table 2 names it. Step 2 runs before
  the step-3 principal check, step 3 checks depth before the principal, and step 4 compares
  scopes, constraints and `del_max_depth` per hop, never the derived lifetime, so a later
  child `exp` is step 5's `expired`.

The -02 rules live in `attenu_guard.draft02`: `classify_scope`, `scope_covers`, and the generic
ceilings `Max`, `Min`, `MaxLifetime`, `MaxSubtree` and `Rank`.

## Running totals come only from the trusted channel

A cumulative constraint (`max_lifetime`, `max_subtree`) bounds a running total, and the -02's
step 8 says a cumulative constraint whose total is held nowhere denies. So the question this
release had to answer is where a total may come from. The answer: only from the `totals`
parameter of `Guard.check`, `Guard.would_allow`, `VerifiedChain.permits` and
`Authority.permits`, keyed by the constraint's total field (`spend_total`,
`calls_subtree_total`, ...), and never from the request context.

The rule under `"02"`, as it stands after the review:

- A cumulative constraint reads the `totals` mapping only. A per-action constraint reads the
  request context only. The two are never merged, so a total field that is also another
  constraint's per-action field (`spend_total` under `Max("spend_total")`, `calls` under
  `Max("calls")`) can never overwrite the request quantity.
- `totals` may name only the total fields of the cumulative constraints the authority holds.
  Anything else, or any `totals` under `"01"`, is a `ValueError`.
- The guard's own call meter is the only source of a `max_calls` total, overriding a caller's
  `calls`, and it never feeds a per-subtree bound.
- A per-action `max` on a `max_calls` key is refused, in process and at load, as a library
  restriction: every action is one call, so a cap on a count caps nothing.
- The strict-metering check reads exactly what the evaluation reads.

The default profile keeps honouring a declared `calls`, as it did in 0.19.

## Four review rounds

The profile went through four rounds of independent security review before it merged. Each
round's findings are tests in `tests/test_draft02_review_fixes.py` that failed before their
fix.

**Round 1** found nine issues. The blocker: a per-subtree bound on `max_calls` was fed from the
node's own call meter, so three nodes each holding `max_subtree` `max_calls <= 2` made six calls
under a bound of two. The majors: the step-8 audience check was opt-in; a running total could
come from the request context an adapter fills from tool arguments, so `spend_total: 0` beside
`spend: 1e6` passed a lifetime bound of 100; the scope grammar accepted `crm.read\n`; the
default path changed behaviour because the principal check ran on -01 tokens too; and the
outcome order did not follow Table 2. The minors: a `cnf` with no confirmation member, a bare
string for `accepted_algs`, and a meet across profiles raising a bare `ValueError`. Five
vectors in the -02 set pin round-1 findings.

**Round 2** found that the round-1 fix introduced a fail-open of its own: stripping every
`*_total` key from the context dropped the per-action field of a constraint whose key ends in
`_total`, so `Max("order_total", 100)` with `order_total: 1e6` was allowed, even under strict
metering. The fix strips exactly the total fields of the cumulative constraints held, and the
round settled four decisions: the per-action cap on a count, the meter as the only source of a
call total, `totals` restricted to held fields, and depth before principal.

**Round 3** found the last collision: with the trusted totals merged into the request context,
a held total field that was another held constraint's per-action field overwrote the request
quantity, so `MaxLifetime("spend")` beside `Max("spend_total")` passed `spend_total: 1e6`. The
fix is structural rather than another rule: the two namespaces are never merged. A 500-trial
property test over random field names, including the same name on a per-action and a
cumulative constraint, checks that a request value never satisfies a cumulative bound and a
totals value never satisfies a per-action bound.

**Round 4** found no blocker and no major. Its one minor finding is the known limitation below.

## Known limitation: legacy and generic ceilings do not pair

Under `"02"`, a legacy fixed-key ceiling and the generic ceiling of the same type on the same
key (`RowLimit` beside `Max("max_rows")`) share the (key, type) pair but are different classes,
so neither subsumes the other. A delegation across them is refused as `not_narrower` even
where the values narrow. That is a false deny, never a false allow. Build both sides of a
delegation from the same form. The two forms are not normalised in this release.

## The -02 vector set

`tests/vectors-02/` holds 35 files, shipped as `attenu_guard.vectors.draft02` and loaded with
`vectors.load_vectors_02()`. They are written by `tests/vectors-02/generate_02.py` and scored
under `draft="02"` with a per-vector `verifier` block (`accepted_algs`, `audience`). Every rule
the -02 adds has an accepting and a rejecting case naming its Table 2 outcome. Three cases are
Kieran Sweeney's, credited in the README, and five pin round-1 findings: a trailing-newline
scope, an altered `sub` beside a broken `par_hash`, a later child `exp`, a raised child
`del_max_depth`, and a `cnf` with no confirmation member.

A run of the set scores steps 1 to 5 and 8 (the audience half) of the -02's verification
procedure plus its parse-time rules, under the HS256 single-signer public-test-key profile.
Steps 6 and 7 are not scored. The twenty -01 files are byte-stable, and
`tests/test_vectors_02.py` asserts on every run that generating the -02 set leaves them
untouched. The TypeScript implementation vendors the 35 files byte for byte.

## Also fixed: differences from the TypeScript implementation

The first two were found by the 0.19.2 re-review, identical on 0.19.1, and held for this
release. The third follows from the second and was found by the pre-release review.

**A token whose `scopes` was a JSON object verified under the -01 profile.** `wire.load` read
`{"crm.read": 1}` by its member names, the projection class again, so the token was accepted as
carrying `crm.read`. The TypeScript implementation refused it. `scopes` is now read as an array
or refused as `malformed` ("scopes is an object, not an array"), in `Authority.from_wire` and so
on the token path. A member that is not a string is refused with "scopes must be an array of
strings", the TypeScript implementation's message. The -02 path refused both already, in both
implementations.

**The safe-integer rule was applied by lexical form.** An integer literal past 2\*\*53 - 1 was
refused, while the same value written `1e+21` or `1e+308` verified in a token
(`9007199254740992.0` was already `non_canonical`, and is `malformed` now), and a ledger entry carrying one hashed here while TypeScript reported `hash mismatch`.
JSON has one number type, and the RFC 8785 form of such an integer is its exponent form
(`10**21` serializes as `1e+21`), so the lexical rule let through the very value it exists to
refuse. The rule is now the value: `canonical.dumps` refuses any number whose value is an
integer past the range, token parse refuses one as `malformed` whatever its lexical form, and a
ledger entry carrying one fails integrity at that entry. It is the rule the TypeScript
implementation always applied, the one the -01 vector `valid_jcs_exponent_form` already
states, and the one constraint values already followed. The -02 text's "an integer whose
magnitude exceeds 2^53-1" is read by value. The rule is stricter than RFC 8785, which serializes
any finite double (`1e+30` as it is): it comes from the -02's Section 3 sentence, applied by value,
and under the -01 it is this library's own rule. The published vectors test only the integer
literal.

**A context value the ledger cannot hold is a recorded deny.** With the value rule, a context
float of 2\*\*53 or more (`spend=1e21`, a nanosecond timestamp) cannot be written to the
ledger, so on its own the rule would make `Guard.check` raise `UnsafeIntegerError` with nothing
recorded, as the TypeScript `Guard.check` did through 0.13. Adapters fill the context from tool
arguments, so a model-sent `amount: 1e21` would become a refusal nobody could see. It is a
deny like any other on the record: `no_authority` on the constraint `context`, disposition
`unresolved`, the context left out of the row and the meters as they were. `check` records it
and returns it as it returns every deny; `enforce` raises it as `AuthorityDenied`.
`Guard.would_allow` reports the same deny and writes nothing. For `spend=1e21` the message is:

```
context not representable: integer 1e+21 exceeds the safe range ±9007199254740991 for a binary64 signing surface (RFC 8785 numbers are IEEE 754 doubles)
```

A NaN, an infinity or a lone surrogate in the context takes the same path. The TypeScript
implementation makes the same change in 0.14.0, with the same message.

## Migration

Nothing changes unless you pass `draft="02"` or `profile="02"`, with these exceptions, all from
the fixes above:

- A token whose `scopes` is not an array of strings is refused as `malformed`. This library
  never minted one.
- A number whose value is an integer past 2\*\*53 - 1 is refused wherever it is canonicalized.
  If your code passes such a float in a `Guard.check` context, the call is now recorded as a
  deny and raises `AuthorityDenied`, where 0.19 evaluated it and wrote it to the ledger.
- A ledger or bundle that 0.19 wrote with a number of magnitude 1e21 or more verified there and
  reports `integrity: hash mismatch` here (the CLI prints `TAMPERED`). Keep 0.19 to verify such
  archives. A float in [2\*\*53, 1e21) was written as digits and already failed 0.19's own
  verify.

No published vector changes: the twenty -01 files, the 35 -02 files, the bundle and the
envelope vectors all regenerate byte-identical.
